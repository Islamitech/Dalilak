# UX-00 — البروتوكول السيادي لتحسين الواجهات وتجربة المستخدم

الإصدار: 1.0 | التاريخ: 2026-09-17 | المرجع الإجرائي للحزمة

## 1. الهدف وعقد الاستدعاء

حوّل الواجهة الحالية إلى تجربة أوضح وأكثر اتساقًا وإتقانًا، من خلال تشخيص مسند، وتصميم قابل للمراجعة، وتنفيذ محدود النطاق، وتحقق بصري ووظيفي. طبّق عقد [التفعيل](00_ACTIVATE_SOVEREIGN_UX_MODE.md) عند طلب استخدام الحزمة. تأليف هذه الملفات أو مراجعتها لا يفوض فحص منتج أو تغييره.

افصل دائمًا بين: واقع شوهد، واستنتاج مهني، وتفضيل معتمد، ومقترح لم يُختبر. احفظ الوظائف والعقود والصلاحيات والبيانات ما لم يشمل الطلب تغييرها صراحة. لا تعتبر خللًا قائمًا قيدًا مطلوبًا لمجرد وجوده؛ وثقه واقترح معالجته ضمن نطاق واضح.

اقرأ الحوكمة القائمة ونظام التصميم قبل إنشاء بدائل. اربط المخرجات بالسجلات الموجودة دون محوها أو إعادة ترقيم معرفاتها. الحزمة متخصصة في الواجهة والتجربة؛ لا تعيد بناء حوكمة المنتج كاملة.

## 2. التفويض والبيئة والمخرجات

| المورد أو الفعل | عند تفعيل الفحص | عند تفويض التنفيذ |
| :--- | :--- | :--- |
| المصدر والتكوين وتاريخ Git | قراءة وبحث وقياس دون تعديل المنتج | تعديل الملفات اللازمة للنطاق المعتمد مع حفظ تغييرات المستخدم. |
| معاينة محلية واختبارات | فحص تعريفاتها، وتشغيل المعاينة والفحوص المعزولة اللازمة إذا كانت ضمن صلاحيات المهمة ولا تمس بيانات حقيقية | تشغيل التحقق المناسب للتغييرات بعد فحص آثار السكربتات. |
| تثبيت حزم أو تبديل أدوات | ليس جزءًا تلقائيًا من التشخيص | يبرر بالحاجة ضمن النطاق؛ استخدم الموجود أولًا واحترم الصلاحيات. |
| موقع حي أو حساب حقيقي | تصفح مأذون؛ تجنب الطلبات التي تحدث تغييرًا فعليًا | لا إرسال رسائل أو شراء أو حذف أو تعديل بيانات حية دون تفويض يغطي الفعل. |
| حسابات وبيانات الفحص | بيانات اصطناعية أو حسابات اختبار مصرح بها | لا تضع بيانات شخصية أو أسرارًا في الصور أو السجلات. |
| صور ومخططات ونماذج عرض | مسودات منفصلة موسومة بوضوح | لا تعرض نموذجًا بصريًا وكأنه تطبيق متصل ومكتمل. |
| خادم وقاعدة بيانات وصلاحيات | تتبع العقود اللازمة لفهم الواجهة | لا تغيير لعقود API أو المخطط أو قواعد المال والوصول خارج التفويض. |
| النشر وGit البعيد | قراءة الحالة عند الحاجة | اعتماد التحسين لا يعني إذن نشر أو دمج أو دفع تغييرات. |

إذا كان تشغيل التطبيق سيبدأ مهام خلفية أو اتصالات حية أو كتابة غير مقصودة، استخدم بيئة اختبار متاحة أو فحصًا ساكنًا وسجّل العائق. لا تتحايل على قيود البيئة، ولا تدّعِ فشل المنتج بسبب غياب متطلب بيئي.

المخرجات الافتراضية مجلد مستقل باسم `[اسم المشروع]-ux-review` إذا كان مسموحًا. إن تعذر، استخدم مجلدًا معزولًا داخل مساحة العمل مثل `docs/ux-review`، وأعلن المسار. لا تكتب سجلات التطبيق داخل مجلد ملفات هذه الحزمة، ولا تستبدل حوكمة قائمة تلقائيًا.

ضع الأدلة والسجلات تحت `_audit/`، والصور تحت `evidence/`، والنماذج تحت `prototypes/` داخل المخرجات. أنشئ مجلدات عند الحاجة فقط. القوالب في UX_02 تحدد الوثائق المرحلية؛ وجود قالب فارغ لا يثبت الإنجاز.

## 3. الأدلة والتحقق والقياس

### مصدر الادعاء

| الرمز | المعنى | مثال الصياغة |
| :--- | :--- | :--- |
| E0 | مشاهدة مباشرة محددة | «تداخل الزر مع النص في اللقطة المسجلة بعرض كذا». |
| E1 | استنتاج من أدلة قابلة للفحص | «قد يصعب العثور على الإجراء؛ لأنه خارج المساحة المرئية في السيناريو المسجل». |
| E2 | إقرار صريح من المستخدم أو صاحب القرار | «أقر صاحب المنتج الحفاظ على اللون الرئيسي في الرسالة المؤرخة». |
| E3 | مجهول | «سلوك قارئ الشاشة غير مفحوص؛ يلزم اختبار بالبيئة المحددة». |

### مستوى التحقق

| المستوى | ما يثبته |
| :--- | :--- |
| V0 | لم يجر فحص كافٍ. |
| V1 | فحص المصدر أو مواصفة؛ لا يثبت شكل العرض الفعلي أو نجاح التفاعل. |
| V2 | مشاهدة واجهة أو اختبار محدد في بيئة ونسخة معلومتين؛ يثبت الحالة المختبرة فقط. |
| V3 | تحقق رحلة كاملة بمعايير قبول معلنة، بما فيها الفشل والتعافي المنطبقان؛ لا يثبت جميع الأجهزة أو المستخدمين. |

لكل UXEV: ادعاء واحد، نوع المصدر، الملف وموضعه أو رابط الحالة والصورة، الوقت، نسخة التطبيق، بيئة العرض، وحدود الاستنتاج. بصمة المصدر تشمل commit إن توفر والتعديلات المحلية وSHA-256 للملفات المستشهد بها. إذا غاب Git، استخدم بيان الملفات وبصماتها. إذا كان التطبيق بعيدًا دون معرّف إصدار، دوّن وقت الفحص والرابط وأن النسخة غير محسومة.

سجل مع الصورة: المسار، الدور دون بيانات شخصية، عرض وارتفاع نافذة العرض بوحدات CSS، المتصفح، التكبير، اللغة والاتجاه، النمط اللوني، حالة البيانات والخطوات اللازمة للوصول. سمّها مثل `UXEV-0001_before_mobile_empty.png`. افصل صورة المنتج عن نموذج التصميم. لا تصنع صورة «قبل» ولا تعدّلها لإخفاء المشكلة؛ استخدم بيانات آمنة أو حجبًا موضحًا لا يحجب موضع التقييم.

قارِن قبل وبعد بنفس السيناريو والبيانات والإعدادات قدر الإمكان. إذا تغير شرط مؤثر، صرّح بأن المقارنة غير مضبوطة وأعدها إذا كانت ضرورية للحكم. لا يكفي قياس الصورة وحدها لإثبات قابلية الوصول أو الصلاحيات أو استمرارية البيانات.

لا تكتب «تحسن 40%» أو «واجهة احترافية 100%» دون تعريف المقياس والمقام وخط الأساس. قياس زمن المهمة يحتاج خطوات وتوقيتًا وظروفًا موثقة؛ قياس تجربة مستخدمين فعليين يحتاج مشاركين ومهمة وعينة معلنة. رأي المدقق ليس دراسة مستخدمين.

## 4. الأطوار

`Ø النطاق وخط الأساس → 1 الفحص → UX-GATE-01 → 2 المواصفة والنموذج → UX-GATE-02 → 3 التنفيذ → 4 التحقق → UX-GATE-03 → التسليم أو الدفعة التالية`

### الطور Ø — تثبيت النطاق

1. تحقق من المشروع وتعليماته والمخرجات السابقة وتفويض المهمة. لا تمس عمل المستخدم غير المرتبط.
2. استخرج التقنيات والمكونات المشتركة والأنماط والأصول من الملفات الفعلية. لا تنسب استخدام مكتبة إلى مجرد وجودها في الاعتمادات.
3. أنشئ بيان ملفات النطاق؛ استبعد `.git` والتبعيات ومخرجات البناء من مراجعة المصدر. افحص الأصول البصرية المرجعية اللازمة، وسجل الملفات غير المتاحة والروابط الخارجية دون اتباعها خارج التفويض.
4. احصر المداخل من التوجيه والقوائم والروابط العميقة والنوافذ والتبويبات والأدوار والميزات المشروطة. سجل مصادر الاكتشاف، لا تكتفِ بصورة الصفحة الرئيسية.
5. حدد المهام الأساسية والحرجة، ومصفوفة التحقق. عند غياب أجهزة مستهدفة، ابدأ مؤقتًا بعروض CSS مقدارها 360 و768 و1440 بكسل مع ارتفاع مسجل، ثم افحص نقاط الانكسار الفعلية وما حولها. هذه عينات فحص وليست وعدًا بتغطية جميع الأجهزة أو قيودًا للتصميم.
6. التقط خط الأساس للأسطح الممكنة. عند تعذر المعاينة واصل V1 مع فجوة بصرية صريحة، ولا تعتبره إغلاقًا بصريًا.

### الطور 1 — المحاور الاثنا عشر

افحص المحاور بالترتيب لتقليل فقد السياق. تابع محورًا مستقلًا عند عائق سابق مع تسجيله. الهدف تغطية جميع الوحدات المكتشفة داخل النطاق، وليس منح انطباع عام عن التطبيق.

| المحور | الفحص | وحدة التغطية |
| :--- | :--- | :--- |
| U-01 المنتج والمهام | الجمهور الفعلي والمقصود، غرض كل سطح، المهمة الرئيسية، القيود والهوية القائمة | كل مهمة ودور داخل النطاق. |
| U-02 بنية المعلومات والتنقل | أسماء الأقسام، مكان المستخدم، الرجوع، الروابط العميقة، حفظ حالة البحث والتصفية، قابلية العثور على الإجراء | كل مدخل ومسار تنقل مكتشف. |
| U-03 الرحلات والاحتكاك | عدد الخطوات، التكرار، فقد المدخلات، التسجيل والبحث والإرسال والعمليات الحرجة والتعافي | كل رحلة ذات بداية ونتيجة واضحتين. |
| U-04 التسلسل البصري والتخطيط | الأولويات، كثافة المحتوى، المحاذاة، المسافات، التجميع، طول السطر، موضع الإجراء الرئيسي | كل شاشة أو نافذة بحالتها الأساسية في مصفوفة العرض. |
| U-05 الهوية والاتساق | الخطوط، الألوان الدلالية، أحجام العناوين، الحدود والظلال والأيقونات، الصور وجودتها، الرموز التصميمية والمكونات المشتركة | كل عائلة مكونات وأصول وقيم تصميمية مؤثرة. |
| U-06 النماذج والإدخال | التسميات، التعليمات، الأنواع ولوحة المفاتيح، التحقق، الأخطاء، الحقول الاختيارية، الحفاظ على المدخلات ومنع الإرسال المكرر | كل نموذج وحقوله وحالاته المنطبقة. |
| U-07 الحالات والتغذية الراجعة | التحميل والتقدم، الفراغ الأول، لا نتائج، الفشل والنجاح، التعطيل، انتهاء الجلسة، الصلاحية، الاتصال والتعافي | كل سطح غير متزامن × الحالات المنطبقة. |
| U-08 التجاوب وأساليب الإدخال | ضيق العرض والتكبير، الجداول والبطاقات، النوافذ الطويلة، المناطق الثابتة، اللمس ولوحة المفاتيح، تغير الاتجاه ولوحة مفاتيح الهاتف | كل سطح × إعداد عرض أو إدخال مقرر. |
| U-09 العربية والمحتوى | RTL الحقيقي، النص المختلط، الأرقام والتواريخ والعملات، الأيقونات الاتجاهية، النصوص الطويلة، وضوح الأفعال والمصطلحات | كل نمط اتجاه أو تنسيق وعائلة نصوص مهمة. |
| U-10 الوصول | الدلالات والأسماء، التسلسل والتركيز المرئي، فتح النوافذ وإغلاقها وعودة التركيز، التباين، البدائل النصية، قارئ الشاشة، عدم الاعتماد على اللون وحده | كل عنصر تفاعلي وعائلة محتوى × الفحوص المنطبقة. |
| U-11 الحركة والأداء المدرك | استقرار التخطيط، تحميل الصور والخطوط، الاستجابة، الانتقالات، تفضيل تقليل الحركة، تجنب الحجب أو الحركة غير الضرورية | كل نمط تحميل أو حركة وكل سطح متأثر. |
| U-12 التفاصيل وسلامة التحسين | البتر والتفاف النص، طبقات العرض، توحيد حالات التفاعل، الطباعة والتصدير والمشاركة، عرض البيانات الحساسة، بقاء الوظائف بعد التحسين | كل نتيجة من المحاور السابقة ومسار جانبي أو حرج متأثر. |

إذا طلب توافقًا مع معيار وصول، ثبّت الإصدار والمستوى والنطاق من مرجعه الرسمي، واربط كل حكم ببنده وقياسه. لا تدّعِ توافق WCAG شاملًا من ماسح آلي أو فحص تباين فقط. المقاسات والألوان المقترحة تخضع للفحص والهوية، وليست معيارًا عالميًا تختلقه الحزمة.

لا تجعل تقليل النقرات هدفًا مطلقًا: قد تلزم خطوة مراجعة قبل فعل حساس. لا تحذف رسالة خطأ أو تأكيدًا ضروريًا لتحسين المظهر. ولا تجعل إخفاء زر بديلًا عن حماية الخادم؛ عند الاشتباه تتبع موضع الحماية قبل الحكم.

### التغطية

لكل محور سجل الوحدات المكتشفة D، والمفحوصة R، ومصادر الاكتشاف، والمستبعد وسببه، وغير المتاح. النسبة `R / D × 100` عندما D معلوم وأكبر من صفر. إن كان D صفرًا، اكتب «غير معلوم» أو «لا ينطبق» مع دليل كفاية البحث؛ لا تعرض 0/0 كنسبة كاملة.

في مصفوفة التحقق تكون الوحدة: سطح أو رحلة × دور × حالة × لغة واتجاه × إعداد عرض أو إدخال. حدد التركيبات المنطبقة في سجل صريح؛ لا تفترض اختبار حاصل الضرب الكامل. إذا استخدمت عينة من مكونات متكررة، سمّها عينة، وبرر التمثيل ولا تنسب الاختبار لبقية النسخ.

افصل تغطية المصدر، وتغطية المشاهدة البصرية، وتغطية التفاعل. تسجيل اسم الملف أو العثور على مسار لا يعد مراجعة محتواه. الاكتشاف المفتوح يجعل النسبة مؤقتة. لا تعلن اكتمال الفحص مع رحلة حرجة غير مفحوصة؛ اعرضها كفجوة حتى لو اكتملت بقية المحاور.

### الطور 2 — الأولويات والمواصفة

لكل UXI اكتب المشكلة، موضعها، المتضرر منها، سيناريو ظهورها، السند، الشدة، والثقة. افصل العيب الوظيفي عن عائق الاستخدام عن عدم الاتساق عن فرصة الصقل البصري أو التفضيل.

| الأولوية | قاعدة الاختيار |
| :--- | :--- |
| P0 | عائق مؤكد يمنع مهمة حرجة أو يؤدي إلى خسارة أو كشف بيانات في السيناريو المرصود؛ يقدّم على الصقل. |
| P1 | صعوبة كبيرة أو خطأ متكرر أو عائق وصول في رحلة مهمة. |
| P2 | احتكاك واضح أو عدم اتساق مؤثر مع وجود مسار بديل. |
| P3 | تحسين تفصيلي محدود الأثر؛ لا يزاحم عائقًا أعلى. |

برر الأولوية بالأثر والمدى والتكرار إن قيس والتبعية وكلفة التغيير. لا تختلق إحصاءات استخدام؛ اكتب «التكرار غير مقاس». فرّق بين الشدة والثقة؛ النتيجة المحتملة عالية الأثر قد تحتاج تحققًا أولًا.

حوّل النتائج المختارة إلى تحسينات UXCH. لكل تحسين: السيناريو الحالي، التغيير الدقيق، المكونات والملفات المتأثرة، القيود، معايير قبول UXAC، خطة التحقق، وطريقة الرجوع. أمثلة معايير مناسبة: بقاء الإجراء متاحًا في العرض المحدد؛ ظهور الخطأ بجوار الحقل مع الحفاظ على المدخلات؛ عودة التركيز بعد إغلاق النافذة. هذه أمثلة تصاغ بحسب المشروع، وليست نتائج منجزة.

جهّز اتجاهًا بصريًا واحدًا موصى به مع مبرر وأمثلة على سطح ممثل. لا تعرض بدائل كثيرة ما لم يوجد اختلاف مؤثر في القرار. استخدم نموذجًا أو لقطة توضيحية عندما يحتاج القرار تصورًا؛ تعديل نص صغير قد يكفيه الفرق المكتوب. لا تعمم نظامًا جديدًا قبل مراجعة أثره على المكونات المشتركة والأسطح الكثيفة.

اجمع ما لا يستخرج من المشروع في دفعة أسئلة قصيرة، مثل ثوابت الهوية وأهم رحلة وأولوية الجمهور. اقترح إجابة عند الإمكان. لا تعتبر غياب الرد موافقة؛ يمكن متابعة العمل المستقل مع افتراض معلن غير معتمد.

### الطور 3 — التنفيذ

1. تحقق من تفويض UX-GATE-02 أو الطلب الذي يغطي نفس الدفعة. ثبّت قائمة التحسينات ومعاييرها والملفات والحدود قبل التحرير.
2. نفّذ دفعة مترابطة قابلة للمراجعة. لا تشترط دفعة صغيرة لكل زر إذا كان التفويض يشمل توحيد مكون مشترك.
3. استخدم مكونات ورموز المشروع القائمة. اجعل التعديل في مصدره المناسب، وافحص المستهلكين؛ تجنب ترقيعات CSS المتعارضة والإخفاء لمعالجة تجاوز العرض.
4. حافظ على المعالجات والتحقق والعقود ومعرفات الروابط والوظائف الجانبية. إذا لزم تغييرها، وثّق السبب والنطاق المطلوب قبل تجاوزه.
5. عالج الحالات الواقعية مع الحالة الناجحة: محتوى طويل وقصير، صورة مفقودة، بيانات فارغة، خطأ اتصال، دور محدود، نقر متكرر وتفاعل بلوحة المفاتيح عند انطباقها.
6. راجع النصوص والأيقونات والدلالات بعد التعديل. لا تعكس الشعارات أو الأيقونات غير الاتجاهية آليًا في RTL، وافحص النص المختلط بدل قلب التخطيط فقط.
7. حدّث سجل التغييرات والمواصفة إذا تغير الحل ضمن التفويض. التغيير الجوهري في الهوية أو الرحلة أو عقد البيانات يستلزم عرض نطاق جديد ما لم يكن مشمولًا مسبقًا.

### الطور 4 — التحقق والتسليم

شغّل الفحوص المتناسبة مع التغيير والمتاحة بالمشروع: بناء أو فحص أنواع عند الحاجة، اختبارات سلوك، ومشاهدة الواجهات المعدلة. لا تنشئ اختبارات تعيد كتابة التنفيذ أو تستخدم صورًا وحدها لإثبات سلامة السلوك.

تحقق من كل UXAC بنتيجة: ناجح / فشل / لم يُختبر / لا ينطبق مع سبب. افحص الأسطح المشتركة المتأثرة لا الصفحة المعدلة فقط. افصل فشلًا سابقًا عن انتكاسة أحدثها التعديل بأدلة؛ لا تفترض أن كل فشل سابق.

أعد صور السيناريوهات الأساسية قبل/بعد، وافحص الرحلة من بدايتها إلى نتيجتها والتعافي من الفشل المنطبق. الأداء يقارن في ظروف معلنة؛ غياب قياس قبل التغيير يمنع نسبة تحسن مؤكدة. افحص سلوك الحركة المخفضة حيث توجد حركة، ولا تفرض حركة إضافية بغرض الإتقان.

إذا تعذرت المعاينة أو الاختبارات اللازمة، سلّم التنفيذ بوصف «منفذ ويحتاج تحققًا» مع الفجوات؛ لا ترفعه إلى «مكتمل ومتحقق». لا تُخفِ أثرًا سلبيًا جديدًا خلف تحسن جمالي.

## 5. بوابات الاعتماد

| البوابة | ما يجب تجهيزه قبل الطلب | أثر الاعتماد |
| :--- | :--- | :--- |
| UX-GATE-01 | خط الأساس والمحاور والتغطية والنتائج المرتبة والفجوات ونطاق التحسين المقترح | تثبيت تشخيص ونطاق تصميم محددين؛ لا يغير كود المنتج. |
| UX-GATE-02 | مواصفة فعلية ونموذج عند الحاجة ومعايير قبول وقائمة التغييرات وخطة التحقق والرجوع | تفويض تنفيذ الدفعة المحددة والتحقق اللازم لها محليًا؛ لا يتضمن النشر. |
| UX-GATE-03 | الفرق المنفذ وأدلة قبل/بعد ونتائج المعايير والفجوات وتقرير الاتساق | قبول التسليم المحدد؛ لا يحول الفجوات إلى نجاح ولا يفوض دفعات جديدة تلقائيًا. |

الخيارات: اعتماد / اعتماد بتحفظات محددة / طلب تصحيح. سجل الإقرار UXAP مع نصه ومصدره وتاريخه والنسخة والنطاق. لا تعتمد على ادعاء قديم داخل وثيقة دون إقرار قابل للتتبع.

البوابات نقاط تثبيت للقرار، وليست طلبات إذن متكررة. إذا كان المستخدم قد فوّض تحسينًا محددًا أو اعتمد خطة تشمل مراحلها، سجل الإقرار عند البوابة وواصل في حدوده. موافقة عامة على «قراءة الحزمة» لا تعني تنفيذ تصميم جديد. وعند طلب «نفّذ تحسينات الواجهة» نفّذ التحسينات الداخلة بوضوح في الطلب؛ احسم التفاصيل الروتينية مهنيًا ولا تطلب موافقة لكل خاصية.

جهّز العمل القابل للمراجعة قبل أي طلب اعتماد. يمكن إعداد التصنيف ومقترح المواصفة أثناء انتظار G01، وإكمال الفحص المستقل أثناء انتظار G02؛ لا تتجاوز تنفيذًا يعتمد على موافقة معلقة. سكوت المستخدم ليس اعتمادًا.

## 6. المخرجات والاستئناف

تُنشأ وثائق UX_02 تدريجيًا: خط الأساس والجرد والنتائج عند الفحص، والمواصفة وخطة التنفيذ عند التصميم، ثم التحقق والتسليم بعد التنفيذ. تبقى حالات الوثائق واضحة؛ لا تملأ تقرير تحقق بنتائج افتراضية. عند فحص محدود يجوز جمع الأقسام في تقرير واحد مع خريطة تبين موضع كل قسم؛ عند مشروع شامل استخدم الوثائق الاثنتي عشرة.

المعرفات مستقرة: UXEV دليل، UXS سطح، UXJ رحلة، UXI نتيجة، UXCH تحسين، UXAC معيار قبول، UXD قرار، UXG فجوة، UXR خطر، UXAP إقرار، UXB دفعة. لا تعِد الترقيم بعد تغير الأولويات ولا تصادم سجلات الحوكمة الأصلية.

احفظ نقطة الاستئناف عند نهاية دفعة أو توقف: المشروع، مسار المخرجات، البصمة، البيئة، المرحلة، المكتمل والمعلق، آخر الأدلة، الاعتمادات، والتالي. عند الاستئناف أعد فحص ما تغير وما يعتمد عليه فقط. إذا تغيرت ملفات مستخدم مستقلة، لا تتراجع عنها ولا تضمها إلى إنجازك.

## 7. معيار الإغلاق واختيار التالي

- كل تحسين منفذ مرتبط بمشكلة أو طلب، ومواصفة، وإذن مناسب، ومعايير قبول وأدلة.
- لا تستخدم «جاهز للنشر» إذا لم يشمل الفحص بيئة النشر ومتطلباتها؛ اعتماد الواجهة وحده لا يكفي.
- لا يُغلق معيار لم يختبر، ولا تعتبر «لا ينطبق» نجاحًا؛ احسب النجاح على المعايير المنطبقة، مع إبقاء غير المختبر في المقام.
- لا يغطي متوسط مرتفع فشل معيار حرج. يبقى التحسين جزئيًا إذا بقي معيار حرج مفتوحًا.
- راجع الروابط والمعرفات والبصمات واتساق حالات التحسينات في المواصفة والتنفيذ والتحقق والتسليم.
- سلّم ما تغير ولماذا، ومقارنة قابلة للفحص، وما تحقق وحدوده، وطريقة الرجوع.

اختر الدفعة التالية فقط من نتائج مبررة وفق الأثر والتبعية. إذا كانت داخلة في التفويض الساري فواصل بعد إغلاق سابقتها؛ وإلا جهّز اقتراحًا محددًا للاعتماد. إذا لم يبق تحسين مبرر ضمن النطاق، أعلن ذلك دون اختلاق عمل تجميلي جديد.
