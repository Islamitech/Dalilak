# UX-01 — أوامر إطلاق التحسينات والاستئناف والاعتماد

الإصدار: 1.0 | التاريخ: 2026-09-17

هذه صيغ استخدام تستدعي [UX_00](UX_00_SOVEREIGN_EXPERIENCE_PROTOCOL.md) ولا تعيد تعريف صلاحياته. يبدأ التطبيق وفق [ملف التفعيل](00_ACTIVATE_SOVEREIGN_UX_MODE.md). الأمثلة بدائل؛ لا تنفذها كلها ولا تنفذ الحقول النائبة حرفيًا. طلب مراجعة الحزمة نفسها لا يفعّل تحسين منتج.

## 1. بدء الفحص والتخطيط

```text
طبّق حزمة الوضع السيادي للواجهات وتجربة المستخدم على: [جذر المشروع أو رابط التطبيق].
الحزمة: [مجلد الملفات الأربعة].
المخرجات: [مسار مسموح، أو حدد الأنسب وأعلنه].

ابدأ بالبصمة والحوكمة ونظام التصميم وخط الأساس، ثم افحص U-01 إلى U-12.
ركز على المهام الفعلية والاتساق واللمسات الاحترافية والعربية والتجاوب والوصول.
وثّق الأدلة والتغطية والفجوات، ورتب النتائج بحسب أثرها على المستخدم.
جهّز UX-GATE-01 بنتائج فعلية ونطاق تحسين مقترح. لا تعدّل كود المنتج قبل تفويض التنفيذ.
```

النطاق الافتراضي هنا الفحص والتخطيط. يمكن فحص المعاينة في حدود UX_00؛ لا تشغّل أمرًا مجهول الآثار أو تستخدم بيانات حية لإتمام السيناريو.

## 2. تفويض تحسين محدد حتى التحقق

```text
نفّذ تحسينات الواجهة وتجربة المستخدم في: [الشاشات أو الرحلة داخل المشروع].
الهدف: [المشكلة أو النتيجة المطلوبة].
الثوابت: [ما يجب الحفاظ عليه من الهوية والسلوك].

هذا تفويض للفحص والتصميم والتنفيذ المحلي والتحقق ضمن هذا النطاق.
سجّل التفويض في UX-GATE-01 وUX-GATE-02، ثم تابع دون طلب اعتماد مكرر للتفاصيل الروتينية.
جهّز خط أساس ومواصفة ومعايير قبول، ونفّذ التغييرات المترابطة، واختبر الحالات المتأثرة.
اعرض عند UX-GATE-03 المقارنة ونتائج التحقق والفجوات. أي توسع جوهري خارج النطاق يُعرض مستقلًا.
```

يصلح هذا الأمر عندما يعرف المستخدم ما يريد تنفيذه. لا يضم نشرًا أو تغييرًا لعقود البيانات أو أفعالًا حية غير مشمولة.

## 3. صقل بصري مع الحفاظ على الرحلات

```text
حسّن التفاصيل البصرية في [النطاق] داخل [المشروع]: التسلسل البصري، الخطوط، المسافات،
الألوان الدلالية، الأيقونات، المحاذاة، وحالات التفاعل.
حافظ على الهوية والوظائف وتسلسل الرحلات، واستخدم مكونات المشروع ورموزه القائمة.
نفّذ محليًا وتحقق بصريًا ووظيفيًا. إذا ظهر احتياج لإعادة تصميم رحلة، سجله كمقترح منفصل.
```

لا تُدخل حركة أو زخرفة لمجرد ملء مساحة. يرتبط كل تغيير بأثر واضح أو طلب معتمد، ويظل التنفيذ خاضعًا لحدود البيئة.

## 4. إعادة تصميم رحلة

```text
أعد تصميم رحلة [المهمة] للمستخدم [الدور] في [المشروع].
افحص البداية والخطوات والنتيجة والفشل والتعافي وحفظ المدخلات.
اعرض التشخيص، والمواصفة المقترحة، ونموذجًا قابلًا للمراجعة عند الحاجة، ومعايير القبول.
جهّز UX-GATE-02 قبل تغيير الرحلة في المنتج؛ التنفيذ يحتاج اعتماد النطاق المعروض.
```

## 5. معالجة العربية والجوال والوصول

```text
افحص وحسّن [الأسطح المحددة] في [المشروع] للعربية وRTL والعرض الضيق ولوحة المفاتيح.
تحقق من النص المختلط، والتفاف العناوين، والنوافذ، والجداول، والتركيز، وتسميات الأزرار،
والتباين وحالات الخطأ. ثبّت إعدادات الفحص وسجّل غير المتاح.
نفّذ التصحيحات ضمن الأسطح المحددة، ثم سلّم الأدلة قبل/بعد ونتائج المعايير.
لا تصف الفحص بأنه توافق شامل مع معيار وصول دون تحديد المرجع والنطاق والتحقق المطلوب.
```

## 6. استئناف

```text
استأنف تحسينات الواجهة من: [مسار _audit/CHECKPOINT.md داخل مخرجات المراجعة].
تحقق من المشروع والبصمة والاعتمادات والبيئة، واقرأ سجلات الدفعة الحالية.
أعد فحص الأدلة المتأثرة بالتغييرات فقط. اعرض المكتمل والمعلق والقرار القادم باختصار،
ثم واصل الخطوة المأذونة التالية؛ لا تعِد طلب موافقة تغطي النسخة والنطاق بالفعل.
```

## 7. إعادة فحص محور أو سطح

```text
أعد فحص [U-xx أو UXS أو UXJ] في [المشروع].
السبب: [تغيير أو نقص أو تعارض].
حدّث الأدلة والتغطية والنتائج التابعة، وميّز المنقوض عن الجديد وعن غير المحسوم.
لا توسع التنفيذ خارج تفويض الدفعة الساري.
```

## 8. اعتماد بوابة

```text
أعتمد [UX-GATE-01 أو UX-GATE-02 أو UX-GATE-03] للتقرير [معرف التقرير أو بصمته].
النطاق: [الدفعة أو التحسينات المعروضة].
التحفظات: [لا يوجد أو قائمة محددة].
```

إذا كانت بوابة واحدة ونسخة واحدة واضحتين في السياق، اربط الرد بهما دون اشتراط إعادة صياغة شكلية. سجّل أثر الاعتماد حسب UX_00. لا تحول التحفظ إلى تحقق ناجح.

## 9. التحقق من دفعة منفذة

```text
تحقق من الدفعة [UXB] في [المشروع] مقابل مواصفتها ومعايير UXAC المعتمدة.
قارن قبل/بعد في ظروف متطابقة، وافحص الرحلات والأسطح المشتركة المتأثرة.
استخدم الفحوص المتاحة المناسبة بعد مراجعة آثارها، وسجل الفشل وغير المختبر صراحة.
هذه مهمة تحقق؛ لا تغيّر المصدر خلالها ما لم يشمل التفويض إصلاح النتائج.
```

## 10. تدقيق مستقل دون تعديل

```text
دقّق مخرجات تحسين الواجهة في [مسار المخرجات] مقابل [المشروع أو المعاينة].
تحقق من الأدلة والبصمات والاعتمادات والتغطية والروابط ومعايير القبول.
افحص إن كانت ادعاءات الإنجاز تتجاوز ما تثبته الصور والاختبارات.
اعرض النتائج وشدتها وحدودها والتصحيحات المقترحة. لا تعدّل الملفات في هذا التدقيق.
```

## 11. تحديث منظومة تحسينات قائمة

```text
حدّث مراجعة الواجهة في [مسار المخرجات] بعد تغير [الأسطح أو النسخة].
ابدأ بالفهرس ونقطة الاستئناف وتقرير التسليم، ثم افحص الفرق وتأثيره.
حافظ على المعرفات والتاريخ والقرارات، وأنشئ نسخة مراجعة للوثائق المتأثرة فقط.
لا تعتبر اعتماد نسخة سابقة اعتمادًا لتوسيع نطاق جديد.
```

## 12. مراجعة الحزمة نفسها

```text
راجع ملفات حزمة الوضع السيادي للواجهات في [مجلد الحزمة] وحسّن وضوحها واتساقها وقابليتها للتطبيق.
هذا طلب لتعديل البروتوكول نفسه؛ لا يفعّل فحص مشروع أو تحسين واجهته.
احفظ الأصل أو نسخة سابقة، ثم اذكر التغييرات وحدود التحقق.
```

## معيار الرد

عند التطبيق قدّم عملًا فعليًا أو قرارًا محددًا بعد تجهيز نتيجته. عند التعذر سمّ العائق وأثره وما يلزم لإغلاقه، وتابع المستقل الممكن. لا تستبدل العمل بعبارة «تم التفعيل» أو بملخص للملفات.
